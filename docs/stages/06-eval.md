## 一、为什么需要评测

没有评测，"优化"就只是感觉。前五个阶段做的每一次改动（关闭推理、
修候选集 bug、加工具层、加 Copilot）都能验证"**没坏**"，
但没法回答"**好了多少**"。

这个阶段补上两样东西：

| 要回答的问题 | 靠什么 |
|---|---|
| 改动有没有破坏契约？ | 一套**确定性断言**（门禁） |
| 改动的质量影响是什么？ | 一个**非门禁**的 LLM 裁判 |
| 到底好了多少？ | `--baseline` 打印差值 |

## 二、小白版原理：为什么门禁只能用确定性断言

评测最容易犯的错，是拿"主观质量"当门禁。本项目**刻意不这么做**：

| | 确定性断言 | LLM 裁判 |
|---|---|---|
| 例子 | 返回了 5 个商品吗？文案有违禁词吗？ | 文案写得好不好？ |
| 可复现 | ✅ 同一个输入永远同一个结果 | ❌ 同一个输入两次可能不同 |
| 能当门禁吗 | ✅ 能 | ❌ **不能** |

**为什么裁判不能当门禁**：文案 Agent 跑在 `temperature=0.9` 上 ——
系统里输出最噪的一环。拿一个自带随机性的东西当门禁，
会产生大量假报警，**让整套评测失去可信度**。

> 所以裁判是**非门禁**的：跑了不影响通过率，只用来"看方向"。
>
> **这也是一个可以讲的判断**：
> "我保留了 LLM 裁判，但让它非门禁 —— 因为它的方差会掩盖真正的回归。"

### `python/eval/runner.py` —— 断言与报告

**面试考点**: 门禁的判定标准、评测可比性、报告的身份信息

```python
def check_case(case, body) -> list[str]:
    """返回失败原因列表。空列表 = 通过。"""
    # 1. 商品数量契约
    if len(products) < a["min_products"]: failures.append(...)
    if len(products) > num_items:        failures.append(...)   # 不能超发

    # 2. 商品 ID 必须真实存在
    unknown = {p["product_id"] for p in products} - known_ids

    # 3. 文案必须逐商品对应（不多不少）
    if want != got: failures.append(...)

    # 4. 违禁词 —— 【直接复用业务代码里的清单】
    from agents.marketing_copy_agent import FORBIDDEN_WORDS
```

**第 4 条有个刻意的做法**：违禁词清单是 `import` 业务代码里的那一份，
**不重新声明**。

> 理由：合规是硬要求。**重复声明一份 = 将来两处规则会不一致**，
> 而评测用的还是旧规则 —— 那比没有评测更危险。

### 报告必须带身份信息

```python
"meta": {
    "git_sha": ...,
    "model": settings.llm_model,
    "pricing_fingerprint": get_pricing().fingerprint(),
    "thinking_exempt": settings.llm_thinking_exempt_agents,
    "mcp_wms_enabled": settings.mcp_wms_enabled,
}
```

**为什么**：模型换了、价格表改了，所有数字都会变。
**不带身份信息的对比是假的。**

对比时还会主动检查一遍：

```
⚠️  可比性告警：
    - 模型不同: deepseek-flash -> deepseek-v4-pro
    - 价格表不同 —— 成本对比不可比
    - 推理豁免名单不同: 'marketing_copy' -> ''
```

### 结果写在 `python/` 外面

`eval_results/` 在**仓库根目录**，不在 `python/` 下。

**理由**：`uvicorn --reload` 会盯着工作目录树里的 `*.py`。
在跑评测时编辑任何 `.py` 会重启应用、杀掉进行中的请求，
制造出"某条用例失败"这个**纯粹由基础设施造成的假象**。

## 四、最重要的实测：一次结论反转

### 实验设计

阶段 D 里我基于**人工阅读文案**做了个判断：营销文案是创作型任务，
保留推理能换来更贴合商品的文案（实测 A 组有"殿堂级音质""旗舰大屏"这类
产品特征，B 组更泛化）。

**现在评测集能检验这个判断了。** 只改一个环境变量，各跑 10 条用例：

```bash
# A 组：文案保留推理（当时的默认）
ECOM_LLM_THINKING_EXEMPT_AGENTS=marketing_copy python -m uvicorn main:app
python -m eval.runner

# B 组：全部关推理
ECOM_LLM_THINKING_EXEMPT_AGENTS= python -m uvicorn main:app
python -m eval.runner --baseline <A 组报告>
```

### 结果

```
与基线对比：
  通过率           100%  -> 100%
  延迟 p50 (ms)    8030  -> 2788      ↑改善
  延迟 p95 (ms)   14880  -> 3997      ↑改善
  平均成本 ($)   0.002495 -> 0.00056  ↑改善
  输出 token p50   1720  -> 318       ↑改善
```

**2.9 倍延迟、4.1 倍成本改善，通过率保持 100%。**

### 但通过率抓不到质量变化

注意 `通过率 100% -> 100%` —— **确定性断言对文案质量是盲的**。
所以又跑了一次 LLM 裁判（用**不同的模型** `deepseek-v4-pro`，避免自我偏好）：

| 用例 | 保留推理 | 关推理 |
|---|---|---|
| rec_001 | 3.5 | **4** |
| rec_002 | 3 | **4** |
| rec_003 | **4** | 3.5 |

**裁判认为关推理的版本在 3 条里 2 条更高** —— 与我人工阅读的结论相反。

### 结论与做法

| | |
|---|---|
| 质量差异 | **在本样本量下不可测**（每条只有 1-2 个样本，3.5 vs 4 是噪声） |
| 性能与成本收益 | **确定的**（2.9 倍 / 4.1 倍，10 条用例） |
| 决定 | **默认改为不保留推理**，保留一行配置可回退 |

**判断依据**：证据对质量不确定、对成本确定时，**选成本低的一侧，保留回退开关**。
而且现在有评测集了 —— 真有质量回归，能被发现。

### 这一段的真正价值

不在于"选对了哪个"，而在于：

> **先做了一个有依据的判断，然后建了一套能检验它的机制，
> 最后按证据改了自己的结论。**

这比一开始就选对更有说服力 —— 因为它展示的是一个**可重复的工作方式**，
而不是一次运气。

> ⚠️ **诚实说明**：`n=3` 的裁判结果**不能证明**"关推理质量不差"，
> 只能说明"**在这个样本量下测不出差异**"。要下更强的结论需要更多样本。
> 这一点必须写清楚，否则就是拿一个小样本当大样本用。

## 六、这一步在简历上怎么写

> 构建评测闭环：10 条 golden set + 确定性断言门禁（商品数量契约、文案逐商品对应、
> 违禁词复用业务代码清单）+ 报告身份信息（git SHA / 模型 / 价格表指纹）保证前后可比；
> 另设【非门禁】的 LLM 裁判评主观质量 —— 因文案 Agent 跑在 temperature=0.9，
> 把随机性引入门禁会产生假报警。
> 基于该闭环完成一次结论反转：将文案 Agent 的推理关闭，
> 实测延迟降低 2.9 倍、成本降低 4.1 倍，而质量差异在 n=3 下不可测。

**为什么这条值得写**：
① 它体现的是**用数据驱动决策**的能力，不是"我会写测试"；
② "非门禁裁判"是一个**有取舍的判断**，能展开讲方差与可信度的关系；
③ **结论反转**这个细节最值钱 —— 它证明的是工作方式，不是运气。
