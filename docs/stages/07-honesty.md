## 一、为什么这一步非做不可

这个项目早期的 README、简历模板、面试指南里有一批**没有实测支撑的数字**。
它们不是"稍微夸张"，而是**面试时的地雷**：

| 说法 | 面试官一问就穿帮的方式 |
|---|---|
| "推荐 CTR 提升 15%" | "你怎么测的 A/B？" —— 而 A/B 引擎返回的 `config` **从未被读取**，实验目前不影响任何行为 |
| "端到端延迟 P99 < 2s" | "现场跑一下？" —— 实测 p95 是 3,997 ms |
| "Redis Sorted Set 实时特征" | "代码在哪？" —— `feature_store.py` 有 117 行完整实现，但**从未被实例化** |
| "Milvus 向量检索" | "依赖装了吗？" —— `pymilvus` 在 `requirements.txt` 里，但**代码里从未 import** |
| "三语言实现" | "Java 版跑一下？" —— 已删除 |
| "LLM 成功率从 85% 提升到 99%" | "怎么统计的？" —— 没有依据 |

> **核心判断**：一个候选人主动说"这个数字我没测过"，
> 比说一个编的数字然后被问穿，好一百倍。
>
> 而更进一步的、真正加分的做法是：**把编的删掉，把能测的测出来。**

### 3. 把最危险的 Q10 改成真实故事

**原来写的是**（目标值当成了已实现）：

> 四个优化手段：并行化 / 超时熔断 / Redis 缓存（命中率 > 80%，延迟 200ms → 5ms）/ LLM 精简

**现在写的是**（真实的三步，每步都有测量）：

> **第一步：先让重试可见。** 我一度以为某次 63 秒的请求是重试造成的，
> 于是加了 `agent.retry` 事件去验证 —— **结果一次都没触发**，我的判断是错的。
>
> **第二步：定位到真正的瓶颈。** 重复测量同一 prompt 发现
> `input_tokens` 每次精确等于 612（与网络无关）、
> **延迟与推理 token 数的相关系数 r = 0.997**。
> 逐个试关闭手段：`max_tokens=64` 反而更慢（该参数被忽略）、
> `reasoning_effort=low` 无效、提示词要求直接作答省 40%，
> `thinking={"type":"disabled"}` 让单次调用从 9,198ms 降到 981ms。
>
> **第三步：并行化本来就有。**

**这个改动的意义**：把一段"听起来厉害但答不上细节"的文字，
换成了一段**有失败、有反转、有数据**的真实经历。

### 最有价值的三件事（按可讲程度排序）

1. **一次由可观测性驱动的判断修正**：加了 `agent.retry` 事件去验证自己的假设，
   结果事件一次没触发，**推翻了自己**，然后顺着查到了真正的瓶颈（r = 0.997）。
2. **一次基于评测的结论反转**：先判断"文案需要推理"，建好评测集后
   实测发现关掉能省 2.9 倍延迟、4.1 倍成本而质量差异不可测，**按证据改了默认值**。
3. **一次主动否决**：评估现成 SQLite MCP Server 后拒绝采用
   （官方已归档、存在 CWE-89、通用 SQL 入口与确定性要求语义不匹配），自建工具契约。

> 三件事的共同点：**都不是"我做成了什么"，而是"我如何判断"。**
> 这恰恰是面试里最难被问倒、也最能体现工程能力的东西。
